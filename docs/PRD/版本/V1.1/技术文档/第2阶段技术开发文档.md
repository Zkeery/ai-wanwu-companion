## 1. 阶段范围与目标

在 R1 场景与养成内核之上，把「账号、伙伴归属、居住方式、位置与多场景 API、旧花园迁移」正式接入。本阶段仍以后端为主，不新增产品页面；页面体验在 R3 统一改版并联调。

本阶段交付：

1. 手机号验证码登录、后端会话、登出与当前用户查询（含短信适配层）。
2. 伙伴账号归属与全后端权限隔离（所有业务 API 按当前账号校验归属）。
3. 居住方式与成员：独居（私人空间）与同住（共居空间 + 成员关系），伙伴当前位置。
4. 多场景 HTTP API：把 R1 的 `LivingStore` 规则内核接到正式 HTTP，owner_id 由「内部可信输入」升级为「会话可信输入」。
5. 旧花园迁移：旧伙伴单花园转换为家庭庭院私人空间，保留超限旧存档与旧撤销语义，不默认把旧数据分给首个登录用户。

本阶段不做：正式前端、真实短信平台接入（到适配验收时解决平台信息与费用授权）、作品墙与小队（R5）、部署。

## 2. 账号与会话

### 2.1 账号

- `users`：`id`（UUID 字符串，作为 living 的 owner_id）、`phone`（唯一）、`created_at`。
- 手机号仅存规范化后的国内 11 位（`^1[3-9]\d{9}$`），统一去除空格、`+86`/`86` 前缀后入库；不存明文验证码。
- 不采集昵称、密码；登录即用验证码。伙伴名字与账号标识分别管理，不改用手机号作为任何伙伴关联键。

### 2.2 短信验证码（本手册默认值，可默认）

- 6 位数字验证码，服务端生成；入库只存哈希，日志与响应不回显验证码或手机号全号。
- 有效期 300 秒；同一手机号 60 秒内最多发送 1 次；单手机号单日最多 10 次；同一验证码连续校验失败 5 次即作废；校验成功一次性作废。
- 发送由确定性代码执行，模型不参与；验证码生成、存储、过期与校验在服务层，短信发送只走适配层一个动作。

### 2.3 短信适配层

- 定义 `SmsProvider`（`send_code(phone, code)`）；真实平台信息（服务商、AppID/密钥、签名、模板）是本阶段需补齐的外部依赖，密钥走 `.env`，不进仓库、前端或日志。
- 隔离验证使用 `MockSmsProvider`：不真正发短信、固定返回成功，仅用于验证验证码生命周期与登录隔离；测试与验收记录必须注明「模拟发送」，不得冒充真实短信。
- 真实短信接入属于涉及费用与对外发送的动作：接入前先告知费用量级（国内验证码短信通常每条几分钱）并取得产品经理确认；失败、超时、限流须有有限重试与明确错误，不发重复轰炸。

### 2.4 会话

- 登录成功后签发不透明令牌（随机 32 字节 URL-safe），服务端只存 SHA-256 哈希；`sessions`：`token_hash`、`user_id`、`created_at`、`expires_at`、`last_seen_at`。
- 有效期 30 天滑动续期；登出删除对应会话。所有业务接口从 `Authorization: Bearer <token>` 提取会话，未带、过期或伪造返回 401 `unauthorized`。
- 当前为单实例；会话表必须可持久化（重启后仍有效），不依赖进程内存。

## 3. 数据模型与归属

在 R2 迁移中，把 R1 的 living 表纳入主应用统一 metadata 与主数据库（`living_spaces`、`living_receipts`），并新增：

- `users`、`sessions`、`verification_codes`（或等价发送/校验记录）。
- `living_memberships`：`space_id` + `companion_id` 唯一，表示「某伙伴是某共居空间的成员」，只对 `shared` 空间有效。
- `Character.owner_id`：外键 `users.id`，可空（`NULL` 表示历史遗留、尚未归属）。
- `Character.current_space_id`：外键 `living_spaces.id`，可空，表示伙伴当前所在空间。

### 3.1 伙伴标识契约

- `living` 空间的 `companion_id` 使用 `str(character.id)`（现成、唯一、自增不复用），`owner_id` 使用账号 UUID；不再让浏览器声明任意 ID。
- 所有按 `companion_id` 的读取与写入，先解析到 `Character` 并校验 `owner_id == 当前账号`；找不到、不属于当前账号返回 404 `not_found`，不泄露是否存在他人数据。

### 3.2 权限校验（后端强制，不依赖前端隐藏）

- 每个业务接口先取会话得到 `owner_id`，再校验目标资源归属；伙伴、空间、成员关系均按账号隔离。
- 私人空间只能由「同一账号 + 同一伙伴 + 同一场景」访问；共居空间由账号所有，成员伙伴可读取同一份存档并执行照料/布置，但不能操作他人私人空间。
- 未登录一律不返回任何伙伴、聊天、记忆或场景数据。

## 4. 居住方式与成员规则

沿用 PRD F05.1 已确认规则，落成确定性代码：

- **独居**：`private` 空间，`owner_id=账号`、`companion_id=伙伴`，同一账号/伙伴/场景唯一（沿用 R1 唯一约束）。
- **同住**：`shared` 空间，`owner_id=账号`、`companion_id=NULL`，有独立成员列表；同住伙伴共享同一份植物、家具与成长状态，不复制、不重复累计成长。
- 每个伙伴同一时刻只有一个当前位置；加入同住、搬回独居、更换场景都保留离开的空间。切换成功才更新位置与画面，失败仍留原处。
- 切换位置前校验：目标空间属于当前账号，且（private）其 `companion_id` 为当前伙伴，或（shared）当前伙伴是成员；否则返回 `forbidden`。
- **移除成员 / 退出共居**：解除成员关系，其当前位置若在此空间则清空（需重新选择居住）；不删除空间、物件或其他伙伴。
- **删除伙伴**：删除其私人空间与关联内容（聊天、记忆、图片等，沿用现有级联），解除其共居成员关系，保留账号共居空间、物件与其他伙伴；删除确认文案必须说明此范围。
- **删除共居空间**：移除全部成员关系，成员当前位置若在此空间则清空；只删除该空间与其中物件。
- **删除账号**：级联删除其私人/共居空间、伙伴、会话与验证码记录，属于数据生命周期能力，删除前有明确确认与影响说明。

## 5. HTTP 服务契约

沿用现有统一错误结构 `{"error": {"code", "message"}}`。新增错误码：`phone_invalid`(422)、`code_invalid`(400)、`code_expired`(400)、`rate_limited`(429)、`unauthorized`(401)、`forbidden`(403)；沿用 `invalid_request`/`not_found`/`conflict`/`invalid_action`/`corrupt_state`/`storage_unavailable` 及 R1 的 HTTP 映射（422/404/409/409/500/503）。

### 5.1 账号

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/v1/auth/code` | 发送验证码；限流与格式校验，成功只回「已发送」，不回显验证码 |
| POST | `/api/v1/auth/login` | `phone` + `code`，校验通过签发会话，返回 `token` 与 `user` |
| POST | `/api/v1/auth/logout` | 删除当前会话 |
| GET | `/api/v1/auth/me` | 返回当前账号信息 |

### 5.2 多场景（全部需登录）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/v1/living/spaces` | 当前账号的空间列表（含场景、类型、成员概要） |
| POST | `/api/v1/living/spaces` | 创建空间：`scene_type` + `mode` +（private 时 `companion_id`）；`space_id` 服务端生成 |
| GET | `/api/v1/living/spaces/{space_id}` | 空间快照（沿用 R1 `read_space` 输出） |
| POST | `/api/v1/living/spaces/{space_id}/actions` | 执行操作：`request_id` + `expected_revision` + `command`，沿用 R1 幂等与冲突语义 |
| GET | `/api/v1/living/spaces/{space_id}/members` | 成员列表（仅 shared） |
| POST | `/api/v1/living/spaces/{space_id}/members` | 加入成员：`companion_id`（校验属于当前账号） |
| DELETE | `/api/v1/living/spaces/{space_id}/members/{companion_id}` | 移除成员 |
| DELETE | `/api/v1/living/spaces/{space_id}` | 删除空间（R1 未提供，R2 补齐） |
| GET | `/api/v1/characters/{id}/location` | 伙伴当前位置 |
| PUT | `/api/v1/characters/{id}/location` | 切换位置：`space_id`，校验归属与成员 |

### 5.3 现有路由的登录改造

- `characters`、`chat`、`scene`、`photos` 现有路由统一增加会话依赖与 `owner_id` 归属过滤；未登录返回 401，访问他人数据返回 404/403。
- 现有 3020 离线页面在 R2 后端隔离后暂不可直接使用，属预期过渡：R3 前端联调接入真实登录后恢复。R2 提供**仅本地开发**的过渡方案（见 8.1），不进入正式构建或生产配置。

## 6. 旧数据迁移与回退

引入 Alembic 管理生产迁移（测试仍可用 `create_all`）。迁移流程必须可验证、可回退：

1. 迁移前备份数据库并验证可恢复；记录迁移前数据文件哈希。
2. 结构迁移：建账号/会话/验证码表，`Character` 加 `owner_id`、`current_space_id`，把 R1 隔离库的 `living_spaces`/`living_receipts` 纳入主库统一 metadata，新增 `living_memberships`。
3. 旧花园转换：把现有 `SceneState`（每个伙伴一份旧九类花园状态）转换为 `home` 私人空间的初始存档；伙伴的当前位置设为该私人空间。
   - 旧九类物件映射到家庭庭院物件集，旧花园超出新上限的存档（如树木 > 7）**保留真实数量与旧撤销语义**，不在迁移时裁剪；R1 验证资产（tree/bench）之外的物件种类随迁移补齐到 `home` 场景目录，不能丢件。
   - 旧花园为预设位置、无坐标，迁移时按物件种类分配默认坐标；后续 R3 前端按场景坐标转换，不保存屏幕像素。
4. **账号归属显式建立**：迁移不自动把旧伙伴分配给任何账号，`owner_id` 留 `NULL`；提供显式「认领」入口，由登录用户确认后把无主伙伴归属到自己（这是人工动作，非自动分配）。旧数据在认领前不可见但保留。
5. 幂等标记：迁移表记录版本号，重复执行不二次转换；成功核对（哈希、数量、样例逐项）后才切换路由。
6. 回退：切换前后各保留回退入口与备份；迁移失败不得留半转换状态，数据库回滚或恢复备份。

执行 `backend/.venv/bin/python -m pytest -q`；账号/迁移相关用临时或副本数据库，不触碰原业务库。短信用 mock 适配器验证隔离逻辑，真实短信单独作为适配验收项（需平台信息与费用授权）。

- 数据重启恢复、密钥不进仓库/前端、README 更新、状态更新为必填并实际验证。

## 8. 待确认与默认决策

### 8.1 现有 3020 离线页面的过渡（本手册默认，可默认）

R2 后端隔离后，现有离线页面暂不可用。默认提供仅本地开发的过渡配置（如 `DEV_AUTH_TOKEN` 映射到一个本地开发账号，并显式认领现有无主伙伴），使 3020 预览在 R3 前端联调前继续可用；正式构建不启用。若产品经理希望 R2 期间保留 3020 完全离线体验，需明确，否则按默认执行。
