## 一、阶段目标与范围

将三项已经查明的前后端差异收敛为确定、可测、兼容旧数据的行为。

| 工作项 | PRD 来源 | 阶段完成后应有的行为 |
| --- | --- | --- |
| S1-A 识别候选上限 | F02、第 11 节 | 新识别及读取/恢复接口最多返回 5 个候选，旧对象和已有角色关系不删除 |
| S1-B 文本长度一致 | F04、F08、第 11 节 | 聊天 4000、单条记忆 1000 的限制在前后端一致，越限请求无写库或模型调用副作用 |
| S1-C 树木数量一致 | F05、F06、第 11 节 | 新增树木最多 7 棵；达限不继续增加；旧超限计数保留；有效撤销不被空操作覆盖 |

交付产物：对应代码改动、边界/兼容回归测试、浏览器及恢复检查、证据与文档更新。

本阶段不改模型、Prompt、温度或重试配置，不启用非思考模式；不重做视觉、不新增景物、不开发登录/计费/部署，不处理宠物范围或完整数据留存方案。

主链路片段：选图得到有限候选 → 正常创建不受影响 → 在已有伙伴中输入、保存记忆和种树 → 刷新后数据与界面一致。

## 二、技术适配与开发路径

沿用当前 Next.js + TypeScript 前端、FastAPI + SQLAlchemy + SQLite 后端及现有模型适配。无需新框架、新依赖、后台任务服务或数据库迁移。

采用局部纵向修改：先定义边界和兼容规则，再修后端权威校验与响应，随后更新前端提示和禁用逻辑，最后验证完整交互。前端限制用于及时反馈，后端限制负责保证真实约束。

已存在的九类花园动作、单步撤销、提议确认、生成恢复和流式结束契约保留。原有接口字段与 HTTP/SSE 形态不因本阶段更名。

## 三、现状、问题与设计决策

### 3.1 实施前核对的现状（历史基线）

- 识别解析器逐项校验标签，但没有候选数量上限；照片首次返回、读取与请求恢复各有响应出口。
- ChatRequest、MemoryCreate、MemoryUpdate 只有文本类型，聊天与记忆接口检查空文本，未实施页面同等长度上限。
- 网页聊天输入框上限 4000，记忆输入框上限 1000；原生 maxLength 按 UTF-16 单元计数，直接套用 Python len 可能使表情字符的边界不一致。
- plant_tree 持续递增，GardenWorld 最多绘制 7 棵树；花丛、蘑菇等已有数量限制。
- 场景更新使用写锁；直接新增装饰与确认提议均涉及撤销历史，必须覆盖上限时的空操作。

### 3.2 本阶段实施默认值

| 规则 | 采用值 | 依据与兼容处理 |
| --- | --- | --- |
| 新识别候选数 | 1–5 个 | 遵循 PRD；保持模型原顺序，不新增去重或重新排序策略 |
| 聊天最大长度 | 4000 个 Unicode 码点 | 保留 4000 额度，统一中英文及普通表情的前后端计数 |
| 单条记忆最大长度 | 1000 个 Unicode 码点 | 新增和编辑使用同一约束 |
| 树木新增上限 | 7 棵 | 与当前画面容量一致；旧存档超过 7 棵时保留原值 |
| 撤销 | 最近一次有效操作 | 越限/重复操作不能制造新的撤销记录或抹掉旧记录 |

码点计数是实现约定，不作为面向用户的技术术语。页面仍使用“字数/最多多少字”等普通文案；组合表情可能包含多个码点，应通过同一组边界样例保证一致。

这些细则在开发前确定，实施后按实际结果更新 PRD 状态；本轮已同步三项规则本地通过与真实基本冒烟待验，未把付费验证写成已完成。

## 五、S1-A：识别候选最多 5 个

### 5.1 新识别结果

1. 保留原有模型 JSON 解析、数组类型、标签类型和非空校验。
2. 先完成整份列表的结构校验，再按原顺序取前 5 个；不靠截断隐藏第 6 项以后的格式错误。
3. 只持久化本次确认有效且保留的最多 5 个候选。
4. 空列表、非对象条目、缺少有效标签仍走原有识别失败路径；不新增模型重试以凑够候选。
5. 标签重复的处理维持原行为，本阶段不顺便更改去重语义。

### 5.2 读取、恢复与旧数据

照片首次创建响应、GET /photos/{id}、GET /photos/requests/{request_id} 中的 photo 使用同一响应组装函数，确保首次展示与断线恢复一致。

旧照片已有超过 5 个 Object 时，按稳定的 Object.id 顺序在响应中展示前 5 个，底层记录不删。既有角色仍通过原 object_id 访问，已知对象的创建结果核对接口保持可用；本阶段不把“候选展示上限”误当成删除或禁用旧对象。

响应裁剪必须发生在独立 DTO/列表副本上，不能给 ORM 的 photo.objects 关系直接赋值为切片，以免触发 delete-orphan 删除旧对象。所有读取接口保持无此类写入副作用。

前端做防御性最多展示 5 个，但不能只靠前端切片解决后端问题。恢复旧草稿时若选中对象仍存在，保留其结果核对能力；若页面没有当前可选对象，明确要求重新选择，不偷偷切换到第一个候选。

## 六、S1-B：聊天与记忆输入校验

### 6.1 统一文本规则

- 文本类型错误、缺字段仍走原有 422 invalid_request。
- 去掉首尾空白后为空，保留原有 400 empty_message / empty_memory。
- 长度按准备保存/发送的去首尾空白文本计算，前后端使用同一套空白归一化定义和测试样例；内部空格、换行保留并计数。
- 以 Unicode 码点计数：浏览器不能只依赖原生 maxLength；后端不能把字节数当字数。
- 明确拒绝不成对的代理字符等无法可靠存储/传输的非法 Unicode 输入，返回 422 invalid_request，不能在写库时变成 500。
- 正常中文、英文、换行、普通表情以及组合表情保持原内容，不静默截断或归一化成另一段文本。

统一空白定义以 ECMAScript trim 的字符集合为规范，在 Python 侧显式保持一致，避免仅分别使用 JS trim/Python strip 时产生边界分歧；至少覆盖普通空格、换行、全角空格与 BOM。公共测试夹具给出归一化后的文本及期望码点数。

### 6.2 后端校验顺序

请求解析/类型检查 → 伙伴或记忆存在性检查 → 文本归一化与长度检查 → 数据写入或模型请求。

聊天超长时在开启 SSE 和写入用户消息之前返回普通 JSON 错误；不先写消息再回滚来伪装无副作用。记忆新增和编辑使用同一个校验函数；失败不改变已有内容、更新时间或条数。

| 条件 | HTTP | error.code | 面向用户的信息 |
| --- | --- | --- | --- |
| 聊天为空 | 400 | empty_message | 沿用现有空消息提示 |
| 聊天超 4000 | 400 | message_too_long | 消息不能超过 4000 字 |
| 记忆为空 | 400 | empty_memory | 沿用现有空记忆提示 |
| 记忆超 1000 | 400 | memory_too_long | 记忆不能超过 1000 字 |
| 类型、字段或 Unicode 不合法 | 422 | invalid_request | 沿用统一请求格式错误提示 |

错误外层继续为 {"error":{"code":"…","message":"…"}}，不改变其他接口的错误处理器，不返回原始长文本或堆栈。

### 6.3 前端交互

- 抽出文本计数/校验工具供聊天、记忆新增、记忆编辑共同使用，展示当前计数和超长提示。
- 输入和粘贴过程中保留草稿，允许用户看到并修改超限文本；不为满足上限静默剪掉文字。
- 超长、空白或正在提交时阻止按钮和 Enter 快捷键提交；中文输入法组合输入期间不能误发。
- 保存或发送时仍检查一次，避免只依赖按钮 disabled。
- 后端拒绝时保留草稿，展示返回的可读提示；不能把失败当作消息已保存或记忆已生效。
- 原有对象描述 100 字和名字 40 字规则不在本阶段重构范围内。

## 七、S1-C：树木上限、旧存档和撤销

### 7.1 场景执行规则

| 现有 tree | 种树结果 | 撤销与反馈 |
| --- | --- | --- |
| 0–5 | 增加 1 | 保存操作前状态作为唯一撤销记录 |
| 6 | 变为 7 | 保存 tree=6 的上一步状态 |
| 7 | 保持 7 | 返回已达上限提示，保留原撤销记录 |
| 大于 7 的旧值 | 保持原值 | 不自动减为 7，不再增加；提示历史数量与画面容量 |

不要直接给现有增量代码加 min(old+1, 7)：这会把旧值 9 变成 7，造成数据损失。正确分支是在 old >= 7 时原样返回，否则增加 1。

直接按钮与提议确认必须调用同一个后端规则。保留 SQLite 写锁：从 6 棵并发点击两次，最多得到 7 棵，第二次为无变化操作，撤销仍能恢复到 6。

### 7.2 提议与撤销

- 直接种树达到上限时，不修改场景、撤销历史或其他已保存状态。
- 确认种树提议时即使已达上限，也应消费该提议并返回未新增的反馈；再确认同一提议仍返回 proposal_expired。
- 上限时的确认不能创建“7 → 7”撤销，也不能覆盖此前有效操作的历史。
- 拒绝、跨伙伴、重复确认、刷新恢复和原有六类物件上限测试全部保留。
- 旧存档及其旧撤销记录可包含大于 7 的数量，撤销按原记录恢复，不进行数量归零、裁剪或迁移。

### 7.3 前端展示

- 普通状态显示“树木 X/7”，达到 7 后禁用种树按钮并说明已达上限。
- 旧状态大于 7 时显示“已保存 X 棵，画面展示 7 棵”，保留真实数量，不谎称画面已展示全部。
- 场景插图和辅助阅读名称反映同一保存状态；前端不得用 max=7 覆盖接口里的旧计数。
- 放大花园与详情页使用同一按钮状态、计数和反馈。
- 其余花丛 6、蘑菇 4、水池/长椅/营火/萤火虫各 1 的规则不变。

测试落在现有 test_parsers.py、test_photos_api.py、test_chat_api.py、test_scene_api.py、test_garden_expansion.py，以及 creation/create-companion/companion/memories/garden 的前端测试中；确有独立复用逻辑时再新增测试文件。

## 十二、风险、回退与执行约束

| 风险 | 处理 |
| --- | --- |
| 截断 ORM 关系删除旧对象 | 只裁剪响应副本；测试验证旧 Object 数量和角色关联不变 |
| tree=9 被 min 上限算法降为 7 | 先判断达到上限后原样返回；旧状态与历史不迁移 |
| 空操作覆盖撤销 | 统一比较操作前后状态，只有有效变化才写新的历史 |
| 前后端表情或空白计数不一致 | 共用输入/输出边界样例，按统一规范实现；不靠原生 maxLength 单独兜底 |
| 超限请求先写库或调用模型 | 校验前移，测试断言数据库与模型调用计数无变化 |
| 本地测试误连真实服务 | 明确隔离数据库、端口和空 Key，付费脚本不进入常规测试集 |
| 用户同时在真实开发版操作 | 测试不写用户库；恢复检查只在确认无活动任务时进行；用户新增内容不误判成测试污染 |

回退以本阶段文件改动为单位，不执行全仓 reset、不丢弃其他未提交内容、不恢复数据库旧副本覆盖用户新数据。因为没有结构迁移，回退无需删除表或清空记录。已有用户数据保持当前版本，必要时停止本阶段改动的发布并调查。
