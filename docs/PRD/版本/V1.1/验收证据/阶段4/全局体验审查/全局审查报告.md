# 当前项目全局审查

审查日期：2026-09-21。代码基线：`26115fa`。本轮仅审查和记录，不修改业务代码，不运行付费模型，不提交 Git。

## 1. 结论与检查边界

项目已经具备个人伙伴、账号隔离、聊天、存档、多场景和再创作的工程基础，但当前不能视为一套体验完整、可直接开放的首版。主要阻塞是：新伙伴未选择住处时无法聊天、失败消息恢复会进入死路；主要体验问题是手机聊天入口与实际内容位置不一致，以及场景视觉与角色陪伴目标脱节。

检查了主页面 `3020` 的实际收藏与伙伴数据，以及无费用验收环境 `3028` 的登录、上传生成、再创作、场景创建、物件添加、聊天建议、确认与刷新。代表宽度为 390×844 和 1440×1000。主环境只读页面，不发送真实聊天或生成请求；新增伙伴和场景操作仅发生于隔离测试库。隔离环境使用模拟识别、占位图片和固定种树决策，不能用于判断真实模型效果、速度或语言理解能力。

历史的后端 484 项、前端 149 项通过属于已有自动化结果，本轮没有重跑或修改这些测试。此次发现的问题说明跨模块完整旅程仍有覆盖缺口，历史通过数不等于整体体验通过。

目录继续保持按项目、版本、技术文档和验收证据归档，结构本身没有发现需要大范围重排的问题。

## 2. 功能与流程问题

### F01｜高优先级：新伙伴还没选择生活场景，普通聊天也被拒绝

**已复现，影响 R4 Agent 开启后的流程。** 主环境开关关闭时不据此声称旧聊天同样故障。

复现：在 `3028` 打开原伙伴 → 再创造一个 → 确认 → 进入新伙伴 → 发送“你好”。页面提示“请先为伙伴选择生活场景”，没有回复。页面同时显示“我们的小花园”和“已保存的花园”，用户很难理解为什么还没有生活场景。

原因：`backend/app/scene_agent/chat.py:104–106` 在普通消息执行前强制要求 `current_space`；新生成伙伴没有当前位置。`frontend/components/recreate-companion.tsx:53` 直接进入详情；普通创建结果同样直接提供“开始聊天”。`companion.tsx:82` 在无当前空间时显示旧花园，进一步隐藏了缺失前置条件。

建议：普通陪伴聊天允许没有住处；需要布置时再引导选择场景。创建成功页把“开始聊天”和“选择住处”清楚呈现，不通过一个看似已有存档的花园掩盖尚未选择住处的状态。

证据：[新伙伴聊天阻塞](新伙伴聊天阻塞-390.png)。

### F02｜高优先级：确定被拒绝的消息仍占着恢复记录，改写后无法发送

**已复现。** 接着 F01，把“你好”改成“我们种一棵树吧”，点击发送，提示“上条消息尚未核对完成，请先核对聊天结果”。当前只有“重新加载”，没有“继续处理原消息”或结束失败任务的入口。

原因：`frontend/lib/chat-recovery.ts:21–25` 阻止同一未结束请求使用新内容；状态查询 404 时在第 39 行保留该记录，却返回 `false`。`companion.tsx:86` 的恢复操作只在 `uncertain` 为真时显示。此时原请求在服务端根本未建立，前端却让它继续阻塞新消息。

建议：区分“请求明确被拒绝”和“连接断开、结果未知”。明确拒绝应结束本次预留，保留草稿并允许用户修正；结果未知保留原请求，并持续展示可核对／继续的操作。补充“未选择住处 → 发消息失败 → 改写 → 选择住处 → 重发”的完整测试。

证据：[聊天恢复死路](聊天恢复死路-390.png)。

### F03｜高优先级：手机导航写着“聊天”，实际先进入很长的场景页

**主页面已复现。** 390×844 下，伙伴详情聊天区起点约为文档 Y=1388px，输入框约 Y=1858px；首屏只有伙伴资料、场景入口和场景画布。底部“聊天”链接仍是当前详情地址，不会跳到聊天区域。

原因：`frontend/app/toy-theme.css:16` 在移动端把完整侧栏排到聊天面板前；`frontend/components/mobile-nav.tsx:22` 只链接详情路由，没有聊天锚点或独立视图。

建议：手机端聊天与场景分开呈现。点“聊天”后首屏出现对话与输入区域；场景保留摘要入口，完整布置放到“场景”。桌面可保留双栏。

证据：[手机伙伴详情](伙伴详情-390.png)、[桌面伙伴详情](伙伴详情-1440.png)。

### F04｜中优先级：名字只能在本次创建结果中修改，后续缺少固定入口

**页面和代码核对。** 已有伙伴详情只有再创作、生活场景、记忆、聊天管理；后者只有清空和删除。改名调用仅出现在 `frontend/components/create-companion.tsx:189–193`。再创作成功又直接跳详情，跳过了普通创建的命名区域。

建议：在伙伴名字旁提供稳定的“编辑名字”入口，再创作和普通创建共用命名规则；改名不扣额度、不重绘。不要让用户为改名重新生成。

### F05｜中优先级：验证码发送后马上显示可点的“重新发送”，点击却报频繁

**隔离环境已复现。** 首次发送成功后按钮立即可点，第二次显示“发送太频繁，请稍后再试”。后端限发规则有效，但前端没有说明还要等多久。

原因：`frontend/components/auth-modal.tsx:52` 只依据请求忙碌和手机号禁用按钮，没有冷却倒计时。

建议：成功后显示剩余秒数并禁用；失败时按错误类型恢复操作。保留当前手机号格式校验和单一登录弹窗。

证据：[验证码重复发送](验证码重复发送-390.png)。

## 3. 页面展示问题

### V01｜中优先级：创建页的核心动作被装饰和重复文案推到首屏以下

**已测量。** 390×844 的隔离创建页，文件输入起点约 Y=860px，底部导航从约 Y=776px 开始；用户首屏看不到选照片按钮。页面连续出现大标题、两行介绍、额度说明、步骤、220px 左右装饰图块，再出现“今天想认识谁”和文件输入。

建议：把上传区本身做成可点击的大按钮，首屏包含选照片和额度说明；压缩重复介绍。桌面仍可左右布局。

证据：[创建页](创建页-390.png)。

### V02｜中优先级：物件多时互相遮挡，不容易照料或移动

**主页面已复现。** 当前一个庭院里 13 棵幼苗的卡片集中重叠，文字和水滴互相压住；存在“布置场景 → 选择物件”作为绕行入口，但默认看图点击仍困难。

原因与边界：`LivingScene` 使用固定宽 94px、至少 80px 高的卡片（`warm-theme.css:190`），靠存档坐标定位；既有坐标密集时没有展示层聚合处理。`scene_bridge.py:19–25` 自动位置仅有九个候选，满后循环，后续也可能出现重叠。本轮新建场景的前三个物件能分开放置，不能把“所有新建即重叠”作为结论。

建议：保留用户已保存坐标，增加可识别的叠放选择、缩放或聚合显示；新增自动放置寻找真正可用的位置，空间不足时给出明确反馈。不要直接重排已有用户布置。

证据：[密集场景](伙伴详情-390.png)、[正常少量物件](生活场景-1440.png)。

### V03｜中优先级：场景像物件管理面板，伙伴没有在其中生活的可见表现

**视觉评审判断，附实际页面。** 当前场景是绿色／其他色渐变矩形，加 Emoji、白色卡片和文字；能操作，但缺乏庭院、沙漠、营地的环境特征。场景画布不展示伙伴本身，难以感知“它在这里生活”。无住处时的旧花园插画与进入住处后的卡片式场景，又呈现两种不同的视觉语言。

建议：统一场景呈现方式，先完成一个庭院代表页：明确地面、环境层次、伙伴位置和植物成长形态，再扩展另外两个场景。物件操作面板保留在选中后显示，减少常驻操作说明。

证据：[生活场景桌面](生活场景-1440.png)。实现依据：`frontend/components/living-scene.tsx:182–193`。

### V04｜中优先级：首页说明仍偏抽象，回访用户的收藏又不够靠前

**视觉评审判断。** 未登录首屏只有一个问号吉祥物，没有“真实物品 → 伙伴”的具体示意；有介绍文案，但第一次看到仍需要阅读才能理解。登录后继续展示完整营销首屏，390px 高度下收藏列表在首屏之外，“收藏”导航点进来仍先看宣传区域。

建议：未登录保留用户要求的一个注册／登录按钮，旁边用一组明确标注为示意的物品与伙伴对照解释用途；登录后先展示收藏与继续陪伴，把大幅介绍折叠。不要增加多个注册入口。

证据：[未登录首页](未登录首页-390.png)、[登录后首页](首页-390.png)。依据：`collection.tsx:53–63,73–79`。

### V05｜中优先级：形象展示偏小，辅助文字普遍偏小偏淡

**视觉与样式核对。** 桌面伙伴头像仅 85px 宽，手机 78px；图片不能点击放大，聊天头像仍使用统一花朵。独特形象在最常用的详情页中存在感不足。收藏描述、场景提示、英文装饰常在 8–12px，浅紫灰色与浅背景区分较弱。

建议：增加可放大的伙伴图或紧凑大图；聊天头像使用该伙伴形象。把必要说明与可操作信息提高字号和颜色深度，英文装饰降低数量。淡色背景可以保留，不需要靠降低文字辨识度制造温柔感。

证据：[桌面伙伴详情](伙伴详情-1440.png)、[手机场景选择](场景选择-390.png)。样式依据：`toy-theme.css:9–10,16`、`warm-theme.css:65,73,104,120`。本轮未做完整无障碍合规审计。
