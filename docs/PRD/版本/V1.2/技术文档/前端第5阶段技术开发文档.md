## 2026-09-24 未发送录音的时长与试听进度显示（先写手册）

录音开始时记录单调的本地起点，停止时按实际经过时间确定并保留“约N秒”，避免最后一次200ms计时未刷新而显示过期值。未发送录音试听改为录音区明确的“已播放N秒 / 录音约N秒”、进度条与播放/暂停/继续按钮；进度取音频 `currentTime`，总时长取本次录音计时，不依赖浏览器原生控件的元数据读数。自然结束显示完成与完整进度；试听失败显示就近错误，不把0误报为录音丢失。重录、取消、发送清空与离开仍释放播放资源。不改变录音Blob、上传、识别、发送或后端契约。自动化覆盖6秒录音停止读数、试听进度/暂停/结束及清理；浏览器合成音轨复核6秒播放和手机/桌面布局。真人麦克风录音仍待用户实测。

## 2026-09-24 重新录制后试听失败修复（先写手册）

用户按“重新录制→停止播放→停止录制→试听录音”操作后收到笼统的试听失败提示。隔离浏览器用两条全新的合成音轨按同序复现时，第二条录音有非空数据且正常播放，因此不能把模拟成功当作用户设备问题已解决。现有代码在 `MediaRecorder.stop()` 之后立即关闭麦克风轨道，而最终 `dataavailable`/`stop` 事件异步到达；也未检查合成后的Blob是否为空、所选录音格式是否可由本页音频播放器读取，播放异常统一吞为一个失败句子。按 [W3C MediaStream Recording](https://www.w3.org/TR/mediastream-recording/) 的事件顺序，改为等待本次录制的 `onstop` 收齐最后音频数据后再释放轨道，并在这段时间显示“正在整理录音”，阻止再次录制、识别或试听未完成的内容。

用户补充实际使用 VS Code 内置浏览器。只读检查该失败页的播放器得到 `MediaError.code=4`，解复用错误为 `DEMUXER_ERROR_COULD_NOT_OPEN`。随后在同一内置浏览器用独立合成音轨实测：WebM/Opus（14786字节）与 MP4（15246字节）都生成非空Blob，但音频元素都报不支持；Web Audio `decodeAudioData` 也无法解开WebM，而一段本地构造的标准16kHz单声道PCM WAV可正常读到1秒。这证明 `isTypeSupported`/`canPlayType` 的标称支持不足以保证此内置浏览器能播放 MediaRecorder 产物；不能靠简单切换WebM/MP4解决。

因此在识别到 VS Code/Electron 内置浏览器时，改为从同一麦克风流以 Web Audio 收集单声道PCM，在录音结束时降采样为16kHz、写入16-bit WAV容器；最长60秒约1.92MB，低于现有8MB服务端限制，并与后端已支持的WAV格式一致。音轨只接到零音量输出以驱动采样，不回放用户麦克风；音频只保留在当前页内存。普通浏览器继续走 MediaRecorder，结束时先收齐 `dataavailable` 再释放轨道。两种路径都要检查空Blob，失败时明确区分录音为空、解码不支持、浏览器阻止播放及其他媒体错误，保留文字草稿，不自动发送或上传。重录开始失败时清理新麦克风并保留旧录音；取消/离开时延迟结束事件不得复活旧录音。自动化覆盖WAV头部/时长/大小、空录音、MediaRecorder异步最终数据、重录/取消与错误提示；在 VS Code 内置浏览器以合成音轨复测页面播放。用户真实麦克风质量仍待用户复测。

同页“聊天与音频记录”原本在尚未载入音色试听或历史音频时仍显示0:00播放器和“停止播放”，容易与正在录制的音频混淆。该共用播放器仅在用户实际点开音色试听或一条已发送音频且成功载入后显示，停止按钮明确写“停止音色或历史音频”；未发送录音仍只用录音区的试听控制。页面不自动播放历史录音，也不改变历史读取接口。
